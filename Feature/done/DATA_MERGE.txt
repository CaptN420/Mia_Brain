# HERMES — ALCHIMIE LIBRARY UPDATE / DATA MERGE SYSTEM

## Objective

Implement a dedicated **Alchimie Library Manager** for Hermes.

Alchimie is the structured knowledge/rule layer used by Hermes to represent:

* transformation rules;
* mathematical transformations;
* mirror operations;
* symbolic relationships;
* normalization rules;
* experimental rules;
* validation constraints;
* transformation metadata;
* domain-specific transformations.

The important architectural principle is:

```text
Hermes = reasoning / orchestration

Alchimie = structured transformation knowledge
```

Hermes should consume Alchimie rules, but the agent system should NOT directly modify the canonical Alchimie database.

All library updates must pass through a controlled ingestion and merge pipeline.

The canonical library should contain validated data only.

Example:

```json
{
  "library_version": "1.0.0",
  "rules": [],
  "transformations": [],
  "domains": [],
  "metadata": {}
}
```

Do not allow malformed or unvalidated records into the canonical database.

# 4. Rule representation

Create a structured rule format.

For example:

```json
{
  "id": "mirror.linear.v1",
  "name": "Linear Mirror",
  "type": "transformation",
  "domain": "mathematics",
  "expression": "M(x,c)=2c-x",
  "inputs": ["x", "center"],
  "outputs": ["mirrored_x"],
  "status": "validated",
  "experimental": false,
  "version": "1.0.0",
  "source": "alchimie",
  "description": "Reflection of x around center c.",
  "constraints": [],
  "validation": {
    "tested": true,
    "tests": []
  }
}
```

The schema must remain extensible.

---

# 5. Experimental rules

Alchimie must explicitly distinguish between:

```text
VALIDATED
EXPERIMENTAL
HYPOTHESIS
DEPRECATED
REJECTED
```

For example:

```json
{
  "id": "experimental.infinity.div12",
  "type": "transformation",
  "expression": "INF / 12 -> INF",
  "domain": "extended_experimental",
  "status": "experimental",
  "experimental": true
}
```

Hermes must never interpret:

```text
experimental = true
```

as established mathematical truth.

The rule engine must know the distinction.

---

# 6. Transformation engine

Create a dedicated component:

```text
AlchimieTransformer
```

Its responsibility is to apply rules from the library.

Conceptually:

```python
result = alchimie.transform(
    input_value,
    rule_id="mirror.linear.v1"
)
```

The transformation engine must return provenance.

Example:

```json
{
  "input": 8,
  "rule": "mirror.linear.v1",
  "parameters": {
    "center": 6
  },
  "output": 4,
  "status": "validated",
  "rule_version": "1.0.0"
}
```

This is important because Hermes must know:

```text
What transformation happened?
Which rule caused it?
Which version of the rule was used?
```

---

# 7. Rules are data, not hard-coded logic

Avoid putting every transformation directly into Python code.

Prefer:

```text
JSON / structured data
        ↓
Alchimie Rule Engine
        ↓
Transformation
```

rather than:

```python
if rule == "mirror":
    ...
elif rule == "something":
    ...
```

Python should implement the transformation engine and validation framework.

The actual rule definitions should live in Alchimie.

# 13. Merge behavior

Do NOT simply overwrite records.

Use deterministic rules.

For example:

```text
NEW ID
    → add

SAME ID + SAME VERSION + SAME CONTENT
    → duplicate / ignore

SAME ID + NEWER VERSION
    → candidate update

SAME ID + DIFFERENT CONTENT + SAME VERSION
    → conflict

DEPRECATED RECORD
    → preserve history
```

Never silently overwrite a canonical rule.

# 16. Merge transaction

The merge should behave like a transaction.

Conceptually:

```text
BEGIN MERGE

backup

load canonical library

load incoming data

validate

merge in memory

validate resulting library

write temporary library

validate temporary library

atomic replace

COMMIT
```

If anything fails:

```text
ROLLBACK
```

The canonical library must never be left partially merged.

---

# 17. Atomic writes

Never directly modify:

```text
rules.json
```

while the merge is running.

Instead:

```text
rules.json.tmp
```

then validate it.

Only after successful validation:

```text
rules.json.tmp
      ↓
atomic replace
      ↓
rules.json
```

This protects against crashes and interrupted merges.

---

# 21. Rule versioning

Example:


```text

```

If its semantics change substantially, create a new version.

This ensures old Hermes analyses remain reproducible.


can be represented in Alchimie as:

```json

  "type": "transformation",
  "domain": "experimental_mathematics",
  "expression": "INF / 12 -> INF",
  "status": "hypothesis",
  "experimental": true,
  "requires_validation": true
```

Do NOT represent it as a universally valid mathematical law.

The rule engine must preserve the distinction between:

```text

```

and:


# 36. Critical architecture principle

The Alchimie library is NOT just a JSON dump.

It is a **versioned transformation knowledge layer**.

The architecture should therefore be:

```text
                 ┌─────────────────┐
                 │    NEW DATA     │
                 └────────┬────────┘
                          ↓
                    VALIDATION
                          ↓
                    NORMALIZATION
                          ↓
                    DEDUPLICATION
                          ↓
                    CONFLICT CHECK
                          ↓
                    HUMAN REVIEW
                          ↓
                       MERGE
                          ↓
                    VERSIONED DB
                          ↓
                  ┌───────┴────────┐
                  ↓                ↓
               THINKER          MIRROR
                  │                │
                  └───────┬────────┘
                          ↓
                     ORCHESTRATOR
```

The important separation is:

```text
Agents DISCOVER and USE rules.

Alchimie VALIDATES and STORES rules.

Library Manager CONTROLS changes.

Orchestrator DECIDES whether a rule is relevant.

User controls canonical library updates.
```

```text

   ↓
```

```text
   ↓
VALIDATE
   ↓

   ↓
MERGE
   ↓
```
