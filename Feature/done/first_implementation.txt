# TASK — Implement the Complete Agentic Code Analysis & Fix Workflow

We need to finish the application's main code-analysis workflow.

The application should become a self-contained environment where a user can:

1. load a Python project/folder;
2. analyze it using Workers + Thinker + Orchestrator;
3. generate a proposed fix;
4. inspect the proposed changes;
5. validate/test the fix;
6. apply the fix;
7. rollback the fix if necessary;
8. run the Python project directly from the application.

The user should NOT need to leave the application and manually use the terminal for the normal workflow.

---

# 1. Target user workflow

Implement this workflow:

```text
LOAD PROJECT
     ↓
ANALYZE
     ↓
WORKERS
     ↓
THINKER
     ↓
ORCHESTRATOR
     ↓
ANALYSIS REPORT
     ↓
GENERATE FIX
     ↓
FIX PREVIEW / DIFF
     ↓
VALIDATE FIX
     ↓
APPLY FIX
     ↓
RUN
     ↓
RESULT
```

And:

```text
APPLY FIX
    ↓
ROLLBACK
```

must always remain available when a reversible change exists.

# 6. WORKERS

Workers should remain specialized.

Do not turn the Thinker into a Worker.

Example worker roles:

```text
Syntax Worker
Bug Worker
Dependency Worker
Security Worker
Architecture Worker
Test Worker
Performance Worker
```

Only instantiate workers that are relevant to the project.

Each Worker returns structured findings.

Example:

```json
{
    "worker": "syntax",
    "file": "app/main.py",
    "line": 42,
    "severity": "error",
    "finding": "...",
    "evidence": "..."
}
```

---

# 7. THINKER

The Thinker receives Worker results.

It:

```text
cross-correlates findings
detects contradictions
generates hypotheses
identifies root causes
proposes solutions
evaluates alternative explanations
```

The Thinker is advisory.

It cannot directly modify files.

Its output must contain:

```text
analysis
hypotheses
evidence
alternatives
recommendations
confidence
validation_required
```

---

# 8. ORCHESTRATOR

The Orchestrator receives:

```text
Worker results
Thinker reasoning
Mirror reasoning if available
Validator results
Project context
```

It decides what findings are sufficiently supported.

The Orchestrator must NOT blindly trust the Thinker.

It should classify findings:

```text
CONFIRMED
PROBABLE
POSSIBLE
UNCONFIRMED
REJECTED
```

Then produce the final analysis report.

# 10. GENERATE FIX

The Generate Fix button should work on a selected finding.

Pipeline:

```text
Selected finding
       ↓
Fix Planner
       ↓
Thinker
       ↓
Orchestrator
       ↓
Patch Generator
       ↓
Proposed Fix
```

The Fix Generator must NOT immediately modify files.

It produces a patch.

Preferred representation:

```diff
--- a/app/main.py
+++ b/app/main.py
@@
- old code
+ new code
```

Internally, preserve enough information to reverse the patch.

# 12. VALIDATE FIX

Before Apply Fix, run validation.

The validation pipeline should preferably use a temporary workspace/copy.

Never use the user's live project as the first validation environment when this can be avoided.

Validation can include:

```text
Python syntax compilation
import validation
unit tests
pytest
static analysis
type checking if configured
dependency validation
application startup test
```

Use only tools that are actually available in the environment.

Report:

```text
Validation

✓ Syntax
✓ Imports
✓ Unit tests: 37 passed
✓ Static checks

Result:
PASS
```

or:

```text
Validation

✓ Syntax
✗ Unit tests: 3 failed

Result:
FAILED
```

If validation fails, do NOT automatically apply the fix.

---

# 13. APPLY FIX

Apply Fix should only modify the real project after the appropriate validation policy has passed.

Before modification:

```text
Create backup/snapshot
Verify patch
Verify target files unchanged since analysis
```

Important:

If the files changed since the analysis, refuse to blindly apply the patch.

Display:

```text
Project changed since analysis.

Please analyze again before applying this fix.
```

This prevents stale patches from overwriting user work.

---

# 14. BACKUP / SNAPSHOT

Every applied fix must have a recoverable snapshot.

Possible implementations:

### Preferred

Use Git when the project is a Git repository.

Create a dedicated checkpoint before applying the patch.

Example concept:

```text
agentic-fix/<timestamp>
```

Do not destroy or overwrite the user's existing Git history.

### Non-Git projects

Create an application-managed snapshot:

```text
.project-agent-backups/
    2026-08-11_08-30-12/
```

The snapshot should contain:

```text
modified files
original contents
metadata
fix ID
analysis ID
timestamp
```

Never silently delete backups.

---

# 15. ROLLBACK

Rollback should restore the state immediately before the selected fix.

Example:

```text
Fix #17
Applied:
    app/main.py
    app/utils.py

[ Rollback ]
```

Before rollback:

```text
Are you sure?
This will restore the previous state of:
    app/main.py
    app/utils.py
```

Again, if the user modified those files after the fix, detect this.

Do not overwrite user changes silently.

Use:

```text
SAFE ROLLBACK
```

rather than blindly copying old files over current files.

      │
      ├── FixPlanner
      ├── PatchGenerator
      ├── DiffViewer
      ├── PatchValidator
      ├── PatchApplier
      └── RollbackManager

      │
      ├── PythonEnvironment
      ├── ProcessManager
      ├── Console

Do not put all functionality inside the UI launcher.

The UI should orchestrate the components rather than implement all the logic itself.

# 35. Final acceptance criteria

The implementation is considered complete when a user can perform this entire workflow without opening a terminal:

```text
1. Open application
2. Click Load Folder
3. Select Python project
4. Click Analyze
5. Workers analyze project
6. Thinker cross-checks findings
7. Orchestrator validates/synthesizes findings
8. User selects a problem
9. Click Generate Fix
10. View proposed patch
11. Validate patch
12. Review diff
13. Apply Fix
14. Run project
15. View stdout/stderr
16. Stop project
17. Run tests
18. Rollback fix if necessary
```

The most important principle is:

```text
ANALYZE ≠ MODIFY
GENERATE FIX ≠ APPLY FIX
APPLY FIX ≠ TRUST FIX
RUN ≠ AGENT AUTHORITY
```

The agentic system proposes and reasons.

The application validates.

The user remains in control.

The Orchestrator decides what the agents' reasoning means.

The filesystem is modified only through the controlled FixSystem.

Build this incrementally and preserve the existing architecture wherever possible.
