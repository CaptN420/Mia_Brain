# Captn — Agentic Cognitive Architecture

## Implementation Roadmap & Development Prompt

> **Purpose:** Transform Captn from a basic multi-agent framework into a modular, observable, self-evaluating agentic architecture.
>
> **Development principle:** Build incrementally. Do not rewrite the entire project at once. Preserve existing functionality whenever possible.

---

# 0. Core Vision

The objective is to build an agentic system where the LLM is **one component inside a larger cognitive architecture**, rather than the entire architecture.

The system should separate:

* planning
* task decomposition
* execution
* tool usage
* memory
* evaluation
* criticism
* replanning
* synthesis
* observability

The architecture should allow individual components to be replaced, tested, benchmarked, and improved independently.

### Core loop

```text
USER
  ↓
ORCHESTRATOR
  ↓
PLANNER
  ↓
TASK GRAPH
  ↓
WORKERS
  ↓
BLACKBOARD
  ↓
SECOND THINKER
  ↓
┌───────────────┐
│               │
APPROVE       REPLAN
│               │
↓               └────→ PLANNER
SYNTHESIS
  ↓
MEMORY
  ↓
RESULT
```

---

# 1. Architectural Principles

* [ ] Keep components modular.
* [ ] Avoid tightly coupling the LLM to execution.
* [ ] Separate "deciding what to do" from "doing it".
* [ ] Make agent state explicit.
* [ ] Make important decisions observable.
* [ ] Make executions replayable.
* [ ] Treat workers as temporary execution resources.
* [ ] Allow different models to be used for different roles.
* [ ] Make memory accessible through explicit interfaces.
* [ ] Make transformations deterministic whenever possible.
* [ ] Never require an LLM for something that can be handled deterministically.
* [ ] Preserve backward compatibility with existing Captn components where practical.

---

# 2. Orchestrator

## Objective

Create a central `Orchestrator` responsible for coordinating the entire execution lifecycle.

The Orchestrator should **not perform every task itself**.

It should coordinate specialized components.

### Responsibilities

* [ ] Receive user objectives.
* [ ] Create an execution context.
* [ ] Invoke the Planner.
* [ ] Register the generated Task Graph.
* [ ] Spawn or assign Workers.
* [ ] Monitor Worker execution.
* [ ] Collect artifacts.
* [ ] Invoke the Second Thinker.
* [ ] Handle APPROVE / REVISE / REPLAN / ABORT.
* [ ] Invoke synthesis.
* [ ] Persist the execution history.
* [ ] Return the final result.

### Suggested interface

```python
class Orchestrator:

    async def run(self, objective: str) -> Result:
        ...
```

The Orchestrator should operate primarily as a **state coordinator**, not as an intelligent worker.

---

# 3. Planner

## Objective

Create a dedicated Planner whose responsibility is to determine **what needs to happen**.

The Planner should not execute tools directly.

### Input

```text
User objective
Relevant memory
Available capabilities
System constraints
```

### Output

A structured `TaskPlan`.

Example:

```python
TaskPlan(
    objective="Analyze dataset",
    tasks=[
        Task(
            id="T1",
            type="research"
        ),
        Task(
            id="T2",
            type="analysis",
            depends_on=["T1"]
        ),
        Task(
            id="T3",
            type="validation",
            depends_on=["T2"]
        )
    ],
    success_criteria=[
        "All claims have evidence",
        "No unresolved critical errors"
    ]
)
```

### Requirements

* [ ] Implement structured task generation.
* [ ] Support task dependencies.
* [ ] Support parallel tasks.
* [ ] Support sequential tasks.
* [ ] Support conditional tasks.
* [ ] Define success criteria.
* [ ] Define task priority.
* [ ] Define expected outputs.
* [ ] Define required capabilities.
* [ ] Allow replanning.

```text
T1 ─────→ T2 ─────→ T4
           │
           ↓
           T3
```

### Task properties

```python
Task(
    id="T1",

    type="research",
    dependencies=[],
    priority=5,
    required_capabilities=[],

    success_criteria=[],

```

### Required features

* [ ] DAG-style dependency support.
* [ ] Parallel execution.
* [ ] Dependency validation.
* [ ] Failed-task propagation.
* [ ] Task retry.
* [ ] Task cancellation.
* [ ] Dynamic task insertion.
* [ ] Dynamic task removal.
* [ ] Replanning support.
* [ ] Task status tracking.

# 5. Workers

Workers are specialized execution units.

A Worker should not need to understand the entire system.

Example worker types:

```text
ResearchWorker
CodingWorker
TestingWorker
FileWorker
BrowserWorker
AnalysisWorker
ValidationWorker
```

### Worker contract

```python
class Worker:

    async def execute(
        self,
        task: Task,
        context: ExecutionContext
    ) -> Artifact:
        ...
```

### Worker requirements

* [ ] Workers receive explicit tasks.
* [ ] Workers return structured artifacts.
* [ ] Workers report errors.
* [ ] Workers report confidence.
* [ ] Workers report assumptions.
* [ ] Workers report evidence.
* [ ] Workers do not directly manipulate global state.
* [ ] Workers communicate through controlled interfaces.

* [ ] Worker factory.

* [ ] Worker lifecycle management.
* [ ] Worker cleanup.
* [ ] Worker resource limits.

# 7. Blackboard

Implement a shared Blackboard for controlled inter-agent communication.

Workers should not need direct knowledge of other Workers.

```text
                 BLACKBOARD
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
       Worker A   Worker B   Worker C
          └──────────┼──────────┘
                     ↓
               Second Thinker
```

### Example

```python
blackboard.publish(
    topic="research.result",
    source="worker_03",
    artifact=result
)
```

### Requirements

* [ ] Publish events.
* [ ] Subscribe to topics.
* [ ] Store artifacts.
* [ ] Track artifact provenance.
* [ ] Support versioning.
* [ ] Prevent uncontrolled global mutation.
* [ ] Allow the Thinker to inspect accumulated results.

```python
Artifact(
    id="A42",
    type="research_result",
    data=result,
    source="worker_03",
    confidence=0.84,
    evidence=[...],
    assumptions=[...],
    timestamp=...
)
```

### Artifact metadata

* [ ] ID
* [ ] type
* [ ] source
* [ ] timestamp
* [ ] confidence
* [ ] evidence
* [ ] assumptions
* [ ] dependencies
* [ ] provenance
* [ ] validation status

This allows the system to reason about **results**, rather than only strings.

# 9. Second Thinker

## Objective

Create a second reasoning component whose purpose is **evaluation rather than primary solution generation**.

The Second Thinker should ask:

> Is the current trajectory coherent, supported, aligned with the objective, and safe to continue?

It should not simply regenerate the Worker answer.

### Input

```text
Original objective
Task Graph
Worker artifacts
Evidence
Execution history
Memory
```

### Output

```python
Critique(
    coherence=0.91,
    evidence=0.73,
    goal_alignment=0.96,
    risk=0.22,
    confidence=0.84,
    decision="APPROVE"
)
```

### Supported decisions

```text
APPROVE
REVISE
REPLAN
ABORT
```

### Requirements

* [ ] Implement independent evaluation.
* [ ] Evaluate evidence quality.
* [ ] Evaluate objective alignment.
* [ ] Evaluate internal consistency.
* [ ] Detect missing information.
* [ ] Detect contradictions.
* [ ] Detect unsupported assumptions.
* [ ] Detect high-risk actions.
* [ ] Produce structured critique.
* [ ] Produce a final decision.

---

# 10. Replanning

If the Second Thinker rejects the current trajectory:

```text
EXECUTION
   ↓
CRITIQUE
   ↓
REPLAN
   ↓
NEW TASK GRAPH
   ↓
EXECUTION
```

The Planner should receive:

```text
Original objective
Previous plan
Failed tasks
Critique
New information
Available artifacts
```

### Requirements

* [ ] Preserve previous execution history.
* [ ] Explain why replanning occurred.
* [ ] Avoid repeating known failures.
* [ ] Modify only the necessary parts of the Task Graph.
* [ ] Maintain successful previous results when valid.

# 11. Memory Architecture

Implement three distinct memory layers.

## 11.1 Working Memory

Current execution context.

```text
current objective
current plan
active tasks
recent artifacts
current errors
current decisions
```

* [ ] Implement scoped Working Memory.
* [ ] Automatically clear it after execution when appropriate.

---

## 11.2 Episodic Memory

Stores previous experiences.

Example:

```text
Task X
→ strategy A
→ failed
→ strategy B
→ succeeded
```

Store:

* [ ] Previous tasks.
* [ ] Strategies.
* [ ] Failures.
* [ ] Successful approaches.
* [ ] Execution duration.
* [ ] Relevant context.
* [ ] Outcomes.

---

## 11.3 Semantic Memory

Long-term knowledge.

Examples:

```text
Python patterns
Linux commands
project architecture
known rules
known concepts
```

* [ ] Implement explicit semantic retrieval.
* [ ] Separate factual knowledge from execution history.

---

* [ ] Store alternatives.

* [ ] Store confidence.
* [ ] Store outcome.
* [ ] Link decisions to execution runs.
* [ ] Retrieve similar previous decisions.
* [ ] Use successful historical strategies when appropriate.
* [ ] Avoid repeating strategies associated with known failures.

# 19. Replay System

The system should be able to replay an execution.

Example:

```bash
captn replay 184
```

Replay should reconstruct:

* [ ] Task Graph.
* [ ] Worker lifecycle.
* [ ] Tool calls.
* [ ] Artifacts.
* [ ] Critiques.
* [ ] Replans.
* [ ] State transitions.
* [ ] Final synthesis.

The replay system is primarily for:

* debugging
* evaluation
* research
* reproducibility
* benchmarking

Do not attempt to reconstruct hidden/private model chain-of-thought.

Replay should reconstruct **observable system events and outputs**.

# 21. Tool Layer

Tools should remain separate from reasoning.

```text
REASONING
    ↓
WORKER
    ↓
TOOL INTERFACE
    ↓
TOOL
```

Never allow arbitrary LLM-generated code to automatically gain unrestricted access to the host system.

Implement:

* [ ] Tool registry.
* [ ] Tool schemas.
* [ ] Permission boundaries.
* [ ] Input validation.
* [ ] Output validation.
* [ ] Timeout.
* [ ] Error handling.
* [ ] Audit logging.

---

# 22. Synthesis Layer

After validation, a dedicated Synthesis step should transform validated artifacts into the final answer.

```text
Worker Results
      ↓
Validation
      ↓
Second Thinker
      ↓
Validated Artifacts
      ↓
SYNTHESIS
      ↓
Final Result
```

The Synthesizer should prioritize validated artifacts over speculative ones.

# 25. Model Independence

Do not hard-code the architecture around one model provider.

Support:

```text
Local LLM
OpenRouter
Ollama
API models
Future providers
```

Define interfaces:

```python
class LLMProvider:

    async def generate(
        self,
        messages,
        schema=None
    ):
        ...
```

Different components may use different models.

Example:

```text
Planner       → strong reasoning model
Workers       → inexpensive specialized model
Second Thinker→ independent reasoning model
Synthesizer   → high-quality language model
```

This should be configurable.

# 30. Non-Goals

Do **not**:

* [ ] Turn every component into an LLM agent.
* [ ] Create unnecessary agent-to-agent conversations.
* [ ] Hide execution state inside prompts.
* [ ] Make memory one giant vector database.
* [ ] Allow Workers to mutate global state arbitrarily.
* [ ] Automatically trust Worker output.
* [ ] Treat model confidence as factual certainty.
* [ ] Rewrite the entire project unnecessarily.
* [ ] Add complexity without an observable benefit.

# 32. Final Development Instruction

Implement this architecture **incrementally**.

Before modifying existing code:

1. Inspect the current repository.
2. Identify existing components that already provide part of this functionality.
3. Reuse existing interfaces where possible.
4. Avoid duplicate implementations.
5. Create tests before major architectural changes.
6. Implement one phase at a time.
7. Run the existing test suite after each phase.
8. Preserve backward compatibility unless a breaking change is explicitly justified.
9. Document architectural decisions.
10. Keep the system runnable after every meaningful change.

For every implementation step, report:

```text
CHANGE
------
What was implemented?

WHY
---
Why does this component exist?

INTERFACE
---------
How does it communicate with the rest of Captn?

TEST
----
How was it tested?

NEXT
----
What should be implemented next?
```

The goal is not merely to create more agents.

The goal is to create a **modular cognitive execution architecture** where planning, execution, criticism, memory, transformation, and synthesis are independent systems that cooperate through explicit state, artifacts, events, and interfaces.
